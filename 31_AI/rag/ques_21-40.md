# Google Interview Prep: 20 RAG Questions with Interview-Ready Answers

For your Google Cloud AI Engineer interview, the goal is to demonstrate more than definitions. The interviewer will likely look for production-level reasoning: how you design retrieval, protect enterprise data, diagnose failures, and improve accuracy, latency, and cost.

For each question below, I’ll give you:

- Interview-ready answer: What you can say aloud in the interview.
- Explanation: The technical reasoning behind the answer.
- Google-level follow-up: A practical detail that demonstrates depth.

Try to deliver the main answer in 30–60 seconds, then expand when the interviewer probes further.

## 1. What is RAG, and why do we need it?

Interview-ready answer

“RAG stands for Retrieval-Augmented Generation. It combines information retrieval with a large language model. When a user asks a question, the system retrieves relevant information from an external knowledge source and supplies it as context to the LLM, which generates a grounded response.

We use RAG when answers must be based on private, domain-specific, frequently changing, or verifiable information that may not be available in the model’s training data. It also allows us to update the knowledge base without retraining the model and supports source citations and access-controlled retrieval.”

Explanation: how RAG works

1\. User query

“What is our loan approval policy?”

2\. Retrieve relevant chunks

Vector / keyword search + metadata filters

3\. Augment the prompt

Question + retrieved context + instructions

4\. Generate a grounded answer

Answer based on retrieved evidence, with citations

A typical pipeline is:

`Documents → Parsing → Chunking → Embeddings → Index → Retrieval → Reranking → LLM → Answer`

Google-level follow-up: RAG reduces dependence on the model’s parametric knowledge, but it does not automatically eliminate hallucinations. The retriever can return irrelevant evidence, the context can be incomplete, or the model can misinterpret correct evidence.

## 2. RAG vs. fine-tuning?

Interview-ready answer

“RAG and fine-tuning solve different problems. RAG provides the model with relevant external knowledge at inference time, whereas fine-tuning updates model parameters to improve its behavior, style, or performance on a specific task.

I prefer RAG for frequently changing enterprise knowledge, source traceability, and document-based question answering. I consider fine-tuning when I need consistent output formats, domain-specific behavior, or improved task performance that prompting alone cannot achieve. In some systems, I would combine both.”

| Dimension       | RAG                                       | Fine-tuning                              |
| --------------- | ----------------------------------------- | ---------------------------------------- |
| How it works    | Retrieves external information at runtime | Updates model weights                    |
| New information | Update the knowledge/index                | May require further training             |
| Citations       | Can preserve document/source references   | Not inherently provided                  |
| Behavior/style  | Limited direct impact                     | Can improve task behavior and style      |
| Main costs      | Indexing, retrieval, storage, inference   | Training, data preparation, inference    |
| Best suited for | Enterprise knowledge and changing facts   | Specialized behavior and task adaptation |

Explanation

For an investment banking chatbot, policies and internal documentation change over time. RAG is a natural choice because the knowledge can be updated and access-controlled independently of the model.

If the same application repeatedly fails to produce a required structured output, and prompt engineering is insufficient, fine-tuning may be worth evaluating.

Google-level follow-up: Fine-tuning is not a reliable substitute for a current knowledge base. A fine-tuned model can still have stale facts and may not reliably reproduce exact document contents.

## 3. When would you NOT use RAG?

Interview-ready answer

“I would not introduce RAG when the task does not require external knowledge, such as simple text transformation, summarization of a short user-provided passage, or basic classification. I would also avoid it if a deterministic API, SQL query, or business rule can answer the question more accurately and reliably.

RAG adds ingestion, indexing, retrieval latency, operational complexity, and new failure points. I would use it when the benefits of grounding responses in an external knowledge source outweigh those costs.”

Explanation and examples

- Simple transformation: Rephrase an email → direct LLM call.
- Exact transaction balance: Query the authorized banking system/API instead of semantically retrieving documents.
- Deterministic eligibility rule: Use validated business logic, not an LLM to guess the result.
- Small, supplied context: Ask the LLM to answer from that context directly.
- Highly sensitive action: Use an authenticated, authorized transactional API with validation and audit logging.

Google-level follow-up: The choice is not always RAG versus no RAG. A production application may use a router: deterministic tools for structured facts, RAG for document knowledge, and an LLM for language understanding and response synthesis.

## 4. Explain an end-to-end RAG pipeline.

Interview-ready answer

“I divide a RAG system into an offline ingestion pipeline and an online query pipeline.

During ingestion, I parse documents, normalize the content, preserve structure and metadata, split it into meaningful chunks, generate embeddings, and store the chunks in a searchable index.

At query time, I authenticate the user, apply authorization filters, optionally rewrite the query, retrieve candidates using vector or hybrid search, rerank them, and select the most relevant evidence. I pass the context with the user’s question and grounding instructions to the LLM. Finally, I validate the response, return citations, and monitor retrieval quality, answer quality, latency, and cost.”

Explanation: two separate flows

### Offline ingestion

1. Ingest documents from approved sources.
2. Parse text, tables, images, and document structure.
3. Chunk content and attach metadata/ACL information.
4. Generate embeddings and build vector/keyword indexes.
5. Validate index quality, freshness, and permissions.

### Online query

1. Authenticate user and determine authorized data scope.
2. Retrieve candidates with filters and hybrid search.
3. Rerank and select relevant evidence within the context budget.
4. Generate a grounded answer and attach citations.
5. Evaluate, log safely, monitor, and handle failures.

Google-level follow-up: Re-indexing must handle document updates and deletions, not just new uploads. I would track document versions, use stable source IDs, remove stale chunks, and propagate permission changes promptly.

## 5. How do you select chunk size?

Interview-ready answer

“I select chunk size based on the structure of the documents, the complexity of the questions, the embedding model, and the LLM’s context window. Smaller chunks improve retrieval precision but can lose context; larger chunks preserve context but may introduce irrelevant information and dilute retrieval quality.

I start with a baseline, such as 300–500 tokens for text-heavy documents, then evaluate different sizes and overlaps on a representative query dataset. I compare retrieval recall, precision, answer faithfulness, latency, and token cost before choosing the configuration.”

Explanation

Chunk size is not a universal constant.

- Small chunks: Useful for precise facts, short policies, and targeted answers.
- Large chunks: Useful when meaning depends on surrounding paragraphs or detailed explanations.
- Structure-aware chunks: Prefer document sections, headings, paragraphs, or logical units over arbitrary character counts.
- Parent-child retrieval: Retrieve a small, precise child chunk but provide its larger parent section to the LLM when extra context is needed.

Example: A question asking for a particular policy threshold may benefit from a small chunk. A question comparing several clauses in a contract may need a larger section.

Google-level follow-up: Use a fixed evaluation dataset and tune chunk size systematically. Do not assume smaller chunks always improve retrieval.

## 6. What is chunk overlap?

Interview-ready answer

“Chunk overlap is the content shared between consecutive chunks. It helps preserve information when a sentence, definition, or concept spans a chunk boundary. For example, if the chunk size is 400 tokens and the overlap is 50 tokens, adjacent chunks share 50 tokens.

Overlap can improve retrieval when boundary splitting would otherwise separate related information, but excessive overlap increases index size, redundancy, retrieval noise, and cost. I tune it based on document structure and retrieval evaluation.”

Example

Suppose a document says:

- Chunk 1 ends: “The loan is approved only when the customer’s credit…”
- Chunk 2 begins: “…score exceeds the required threshold.”

Without overlap or structure-aware splitting, retrieving either chunk alone may lose part of the rule.

Practical starting point: Try around 10–15% overlap for a baseline, then evaluate. This is a starting heuristic, not a universal requirement.

Google-level follow-up: Prefer splitting on meaningful boundaries first. Overlap is a safeguard, not a replacement for good chunking.

## 7. What is semantic chunking?

Interview-ready answer

“Semantic chunking divides a document based on changes in meaning rather than using a fixed number of characters or tokens. The system evaluates neighboring sentences or passages and creates a new chunk when their semantic similarity drops sufficiently.

It helps keep related information together, which can improve retrieval quality for documents with varying topic lengths. However, it adds preprocessing complexity and cost, so I would compare it with simpler structure-aware chunking using a representative evaluation dataset.”

Explanation

For example, a document might move from:

- Section A: Loan eligibility
- Section B: Interest calculation
- Section C: Repayment penalties

A fixed-size splitter could combine unrelated sections. Semantic or structure-aware chunking aims to preserve each topic as a coherent unit.

Common approaches

- Sentence embeddings and similarity thresholds.
- Change-point detection across consecutive passages.
- Heading-aware or section-aware splitting.
- Hybrid splitting that respects headings and then uses token limits.

Google-level follow-up: Semantic chunking can still produce chunks that are too large or too small. Enforce token limits and evaluate the downstream retrieval and answer quality.

## 8. How do you handle tables in RAG?

Interview-ready answer

“I avoid treating every table as ordinary prose because table meaning depends on its headers, row relationships, units, and sometimes merged cells. I first extract the table structure, preserve headers and units, and convert the data into a representation suited to the query.

For small tables, I may serialize rows with their headers into text. For large or numeric tables, I may store the data in a structured database and use SQL or a data tool for exact calculations. I would validate extraction accuracy and retain source references.”

Example

Original table:

| Loan type     | Interest rate |
| ------------- | ------------- |
| Home loan     | 8.5%          |
| Personal loan | 12%           |

A useful text representation is:

`Loan type: Home loan; Interest rate: 8.5%.`

This preserves the relationship between each value and its column.

For complex tables:

- Preserve table title, headers, row labels, units, and footnotes.
- Keep related rows together or create row-level chunks with repeated headers.
- Use structured querying for calculations, aggregations, and comparisons.
- Retain page number and table ID for citations.

Google-level follow-up: If a question asks “Which product has the highest rate?”, retrieving a table fragment and asking the LLM to calculate may be less reliable than executing a validated SQL query.

## 9. How do you handle PDFs containing images and tables?

Interview-ready answer

“I use a document-processing pipeline that combines text extraction with layout-aware parsing and OCR. For digital PDFs, I extract text and structural information directly. For scanned PDFs, I apply OCR. For complex tables and image-heavy pages, I use layout detection and, where needed, vision-language models.

I preserve page numbers, section headings, bounding boxes or element IDs, and source metadata. Then I create text or multimodal chunks and index them appropriately. Finally, I validate extraction quality because OCR and table parsing errors can directly degrade RAG accuracy.”

Explanation: choosing the extraction method

| PDF content              | Approach                               |
| ------------------------ | -------------------------------------- |
| Digitally generated text | PDF text extraction                    |
| Scanned pages            | OCR                                    |
| Complex tables           | Table/layout extraction                |
| Charts and diagrams      | Vision model or specialized extraction |
| Mixed text and images    | Layout-aware multimodal parsing        |

A vision model may describe a chart, but the pipeline should preserve any extracted numerical values and their source. For financial or regulatory documents, critical numbers should be validated rather than blindly trusted from OCR.

Google-level follow-up: Do not necessarily embed every page as one image. Extract structured content where possible, use image embeddings or captions when appropriate, and keep links to the original page for verification.

## 10. How do you handle very large documents?

Interview-ready answer

“I process large documents incrementally rather than sending the entire document to the LLM. I split them by document structure, index chunks with document and section metadata, and retrieve only the relevant passages at query time.

For questions requiring information from multiple sections, I can use hierarchical retrieval: first identify relevant sections, then retrieve detailed chunks. For broad summarization, I may use a map-reduce or hierarchical summarization approach. I also use versioning, incremental re-indexing, and deduplication to keep the index efficient.”

Explanation

- Targeted questions: Retrieve a few relevant chunks.
- Cross-section questions: Retrieve from multiple sections and synthesize evidence.
- Whole-document summary: Summarize sections, then combine the summaries.
- Updated documents: Re-index changed sections instead of rebuilding everything unnecessarily.

Google-level follow-up: Large context windows do not eliminate retrieval. Sending too much content can increase cost and latency and may cause the model to overlook relevant evidence.

## 11. How do you handle metadata?

Interview-ready answer

“I attach metadata to each chunk so that retrieval can use more than semantic similarity. Typical fields include document ID, title, source, page number, section, document version, timestamp, language, document type, tenant ID, and access-control information.

I use metadata for filtering, access control, freshness, deduplication, citations, and debugging. I also validate metadata during ingestion and define a consistent schema so that missing or inconsistent values do not cause retrieval failures.”

Example

```
metadata = {
    "document_id": "policy_123",
    "section": "Eligibility",
    "page": 12,
    "version": "3",
    "tenant_id": "tenant_A",
    "language": "en"
}
```

Explanation

A query about the latest policy could filter for the active version. A user asking about a specific document could filter by document ID. A multilingual system could use language metadata to improve routing and retrieval.

Google-level follow-up: Metadata quality matters as much as the filtering logic. A filter cannot reliably select the correct version if ingestion assigns incorrect or stale metadata.

## 12. How do you implement access control in RAG?

Interview-ready answer

“I implement access control at the retrieval layer, not just in the prompt. After authenticating the user, the application obtains their authorized groups, roles, tenant, and document permissions from a trusted identity or policy system. It then applies those permissions as mandatory filters before returning any chunks to the LLM.

I also enforce authorization on source connectors and downstream tools, protect cached results, and test for cross-user leakage. The LLM should never decide which documents a user is allowed to access.”

Explanation: architecture

User authentication

Identity provider / verified token

Authorization policy

Resolve roles, groups, tenant and permissions

Filtered retrieval

Only authorized documents/chunks are eligible

LLM generation

Receives authorized context only

Important implementation details:

- Enforce access checks on the server; never trust user-supplied tenant IDs or roles.
- Apply ACL changes and document revocations promptly.
- Partition or scope caches by tenant and authorization context.
- Re-check permissions when fetching source documents or calling tools.
- Log access decisions securely for auditing.

Google-level follow-up: Prompt instructions such as “do not reveal confidential information” are not an access-control mechanism. Unauthorized content must be excluded before generation.

## 13. What is metadata filtering?

Interview-ready answer

“Metadata filtering restricts the candidate documents based on structured attributes before or during retrieval. For example, I can filter by tenant ID, document type, language, date range, document version, or access permissions.

This reduces irrelevant candidates and enforces important constraints. In an enterprise RAG system, I would apply mandatory authorization filters first and then perform similarity search within the eligible document set.”

Example

A query searches for a policy, but only within the user’s authorized department and current document versions:

```
filters = {
    "tenant_id": authenticated_tenant,
    "department": authorized_department,
    "status": "active"
}
```

This is illustrative pseudocode; actual filter syntax depends on the vector database.

Metadata filtering vs. semantic search

- Metadata filtering: “Only documents belonging to Finance and marked active.”
- Semantic search: “Find documents that discuss loan eligibility.”

These techniques complement each other: metadata establishes the eligible scope, while semantic search identifies relevant content within that scope.

Google-level follow-up: Filtering syntax and execution vary across vector databases. Some systems apply filters before approximate nearest-neighbor search, while others may apply them differently. Verify that the database’s behavior meets your recall and security requirements.

## 14. How do you prevent one customer's data from appearing in another customer's response?

Interview-ready answer

“I use defense in depth. Each request is authenticated, and the tenant identity is derived from a trusted token rather than from user input. Tenant isolation is enforced in the retrieval query, storage permissions, document connectors, caches, and tool calls.

I also test adversarial cross-tenant queries, verify that no unauthorized chunks enter the prompt, and monitor for leakage. Depending on the sensitivity and isolation requirements, I may use separate indexes, collections, databases, or projects for different tenants.”

Explanation: common leakage paths

1. Retrieval: A vector query searches all tenants because a filter is missing.
2. Caching: One tenant receives a cached response generated for another tenant.
3. Conversation memory: A session or thread is reused across users.
4. Tools: A database or search tool executes with overly broad permissions.
5. Logging: Sensitive retrieved context is exposed in logs or traces.

How to mitigate them

- Derive tenant identity server-side and fail closed if authorization context is missing.
- Include tenant and permission scope in cache keys.
- Scope conversation state by user, tenant, and session.
- Use least-privilege service identities and enforce downstream authorization.
- Add negative security tests: explicitly verify that Tenant A cannot retrieve Tenant B’s known documents.

Google-level follow-up: A metadata filter is necessary but may not be sufficient for high-sensitivity systems. Choose the isolation model based on threat model, regulatory requirements, operational cost, and the guarantees offered by the underlying infrastructure.

## 15. What is hybrid search?

Interview-ready answer

“Hybrid search combines lexical search, such as BM25 keyword retrieval, with semantic vector search. Keyword search is effective for exact terms, identifiers, product codes, and error messages, whereas vector search is better at matching meaning when the query and document use different wording.

I combine their candidate sets using a method such as Reciprocal Rank Fusion, or RRF, and optionally apply a reranker. I evaluate the hybrid configuration against a representative query set rather than assuming it will always outperform either method alone.”

Example

User query: “What is the failure code for brake sensor XJ-42?”

- Keyword search is good at finding the exact code `XJ-42`.
- Vector search may retrieve related documents discussing brake sensor failures.
- Hybrid search can combine both kinds of evidence.

RRF intuition

RRF combines ranking positions from different retrieval systems:

\\[ \operatorname{RRF}(d)=\sum\_{r \in R} \frac{1}{k+\operatorname{rank}\_r(d)} \\]

Here, \\(d\\) is a document, \\(R\\) is the set of ranked lists, and \\(k\\) is a smoothing constant.

Google-level follow-up: Hybrid search is especially useful when a corpus contains both natural-language content and exact technical terms. Its benefits depend on the data, query distribution, and how the rankings are combined.

## 16. What is reranking?

Interview-ready answer

“Reranking is a second-stage retrieval step that re-evaluates the relevance of an initial set of candidate documents against the user’s query. The first-stage retriever prioritizes speed and retrieves a larger candidate set; a reranker then scores the query-document pairs more precisely and reorders them.

I use reranking when initial retrieval has reasonable recall but the top results contain irrelevant or weakly relevant passages. I then select the best evidence within the LLM’s context budget.”

Example pipeline

`Query → Retrieve top 50 candidates → Rerank → Keep top 5–10 → LLM`

The numbers are illustrative and should be tuned.

Types

- Bi-encoder: Embeds the query and documents separately; efficient for large-scale initial retrieval.
- Cross-encoder: Evaluates a query and document together; often more precise, but more expensive.
- LLM-based reranking: Uses an LLM to judge relevance; flexible but can add substantial latency and cost.

Google-level follow-up: Reranking cannot recover relevant evidence that was never retrieved in the first place. If recall at the initial retrieval stage is poor, fix candidate generation before tuning the reranker.

## 17. Vector search vs. keyword search?

Interview-ready answer

“Keyword search matches lexical terms, often using an inverted index and ranking algorithms such as BM25. Vector search converts queries and documents into embeddings and retrieves items based on vector similarity.

Keyword search is strong for exact identifiers, names, codes, and rare terms. Vector search is strong for semantic similarity and paraphrases. For enterprise applications, I often consider hybrid search because it combines the strengths of both.”

| Dimension       | Keyword search              | Vector search                            |
| --------------- | --------------------------- | ---------------------------------------- |
| Matching        | Terms and lexical relevance | Semantic representation                  |
| Exact IDs/codes | Usually strong              | Can miss exact matches                   |
| Paraphrases     | May struggle                | Often strong                             |
| Index           | Inverted index              | Vector index                             |
| Main challenge  | Vocabulary mismatch         | Embedding quality and semantic ambiguity |

Example

“Reset error E1042” may be found reliably with keyword search, while “How can I recover after the device fails to start?” may benefit from semantic retrieval.

Google-level follow-up: Neither method guarantees relevance. Evaluate retrieval against real queries, especially those containing identifiers, acronyms, multilingual text, and ambiguous wording.

## 18. Cosine similarity vs. HNSW?

Interview-ready answer

“Cosine similarity is a similarity measure used to compare the directions of two vectors. HNSW, which stands for Hierarchical Navigable Small World, is an approximate nearest-neighbor indexing algorithm used to search large vector collections efficiently.

They solve different problems: cosine similarity defines how similarity is measured, while HNSW helps find likely nearest neighbors without exhaustively comparing the query against every vector. They can be used together in the same vector-search system.”

Explanation

Cosine similarity:

\\[ \operatorname{cosine}(A,B)= \frac{A\cdot B}{\\|A\\|\\|B\\|} \\]

- A higher cosine score generally indicates greater directional similarity.
- HNSW builds a graph with multiple navigational layers to speed up nearest-neighbor search.
- HNSW is approximate: it trades some retrieval accuracy for speed and efficiency.
- Search quality depends on index and search parameters, embedding quality, and the chosen distance metric.

Google-level follow-up: HNSW does not replace the similarity metric. If you use cosine similarity with HNSW, the index uses the configured metric while navigating the graph. Some databases support other metrics, such as dot product or Euclidean distance.

Also, similarity is not the same as relevance. A vector with a high score may still be irrelevant to the user’s actual question.

## 19. How do you troubleshoot poor retrieval?

Interview-ready answer

“When retrieval quality is poor, I first separate the problem into ingestion, query processing, indexing, and ranking. I verify that the relevant document was parsed correctly, chunked appropriately, embedded with the expected model, and indexed successfully.

Then I inspect the actual top-k results for representative queries. I evaluate whether the problem comes from missing content, poor chunk boundaries, query-document vocabulary mismatch, incorrect metadata filters, or an unsuitable retrieval configuration. I test changes independently and measure recall\@k and precision\@k against a labeled evaluation dataset.”

Step-by-step debugging

Step 1: Verify ingestion

Was the source document ingested? Was the relevant text, table, or page extracted correctly? Are chunks missing or duplicated?

Step 2: Inspect chunking and embeddings

Are chunks coherent? Are important terms and headings preserved? Are the query and documents embedded using compatible models and configurations?

Step 3: Check query and filters

Are metadata filters too restrictive? Would query rewriting, keyword search, or hybrid search improve matching?

Step 4: Inspect top-k candidates

Is the relevant chunk absent entirely, present at a low rank, or retrieved with insufficient context?

Step 5: Evaluate improvements

Compare retrieval recall, precision, ranking quality, latency, and cost on a fixed test set.

Know these metrics

- Recall\@k: Of all relevant documents, what fraction appears in the top \\(k\\)?
- Precision\@k: Of the top \\(k\\) retrieved documents, what fraction is relevant?
- MRR: How highly ranked is the first relevant result?
- NDCG\@k: How well are results ranked when relevance has different grades?

For example, if 10 documents are relevant and the top 5 contain 4 of them, recall\@5 is \\(4/10 = 0.4\\). If 4 of the 5 retrieved documents are relevant, precision\@5 is \\(4/5 = 0.8\\).

Google-level follow-up: Diagnose before tuning. If the relevant document is missing from the top 50 candidates, reranking the top 10 will not fix the problem. If it is present at rank 30, investigate retrieval ranking and consider reranking.

## 20. How do you troubleshoot good retrieval but bad generation?

Interview-ready answer

“If retrieval is good but the final answer is incorrect, I focus on the generation stage. I inspect the exact context passed to the LLM, verify that it contains sufficient and non-conflicting evidence, and check whether truncation or context ordering removed important information.

I then review the system prompt, grounding instructions, model choice, context length, and generation settings. I instruct the model to answer from the supplied evidence, cite supporting sources, and explicitly state when evidence is insufficient. Finally, I evaluate faithfulness and answer correctness separately from retrieval quality.”

Explanation: debugging by symptom

| Symptom                           | Possible cause                    | Potential fix                                     |
| --------------------------------- | --------------------------------- | ------------------------------------------------- |
| Correct chunks, wrong answer      | Model misinterprets evidence      | Improve prompt, test model choice                 |
| Answer includes unsupported facts | Hallucination                     | Grounding constraints, evidence validation        |
| Model ignores relevant context    | Context overload or poor ordering | Reduce noise, reorder evidence                    |
| Conflicting answers               | Stale or inconsistent sources     | Version filtering, conflict resolution            |
| Answer misses part of question    | Insufficient coverage             | Retrieve complementary evidence                   |
| Wrong citation                    | Citation mapping error            | Preserve chunk/source IDs and validate references |
| Inconsistent answers              | Sampling or model variability     | Tune decoding and evaluate repeatability          |

Practical example

Suppose retrieval returns the correct policy stating that the threshold is 70%, but the LLM answers 75%.

I would:

1. Inspect the exact prompt and confirm that the 70% value is present.
2. Check whether another retrieved chunk contains an outdated 75% value.
3. Ensure the active policy version is selected and conflicting sources are resolved.
4. Make the grounding instruction explicit and require a citation.
5. Re-test against a golden dataset and verify that the response matches the source.

Google-level follow-up: Lowering temperature can reduce variability, but it does not guarantee factual correctness. I would also measure faithfulness, answer correctness, citation correctness, and the system’s ability to abstain when evidence is insufficient.

# Final revision: the key distinctions to remember

These are the follow-up questions that often reveal whether you understand the architecture or have only memorized definitions.

| Interviewer asks                                                    | Your key point                                                                        |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Does RAG eliminate hallucinations?                                  | No. It supplies evidence; the model can still misinterpret or ignore it.              |
| Does fine-tuning add current knowledge?                             | Not reliably. RAG is better suited to frequently updated external knowledge.          |
| Does chunk overlap always improve quality?                          | No. It can increase redundancy and index cost.                                        |
| Does semantic chunking always outperform fixed-size chunking?       | No. Evaluate against the actual corpus and queries.                                   |
| Does HNSW calculate cosine similarity?                              | HNSW is the search index algorithm; cosine similarity is a metric.                    |
| Does reranking improve recall?                                      | Not if relevant documents were never retrieved into its candidate set.                |
| Is metadata filtering the same as access control?                   | No. Authorization needs trusted identity, policy enforcement, and secure data access. |
| Should the LLM decide document permissions?                         | No. Enforce permissions before context reaches the LLM.                               |
| Is a larger context window always better?                           | No. More context can increase cost and distract from relevant evidence.               |
| If retrieval is correct but the answer is wrong, what do you debug? | Context construction, prompt, conflicting evidence, generation, and citations.        |
